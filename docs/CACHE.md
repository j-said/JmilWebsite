# Кешування

Завдання 5. Код: [`api/app/core/cache.py`](../api/app/core/cache.py), [`api/app/api/v1/products.py`](../api/app/api/v1/products.py). Інфраструктура: [`infra/cache.tf`](../infra/cache.tf).

## Що кешується

Найчастіше люди відкривають каталог — `GET /api/v1/products`. У тесті це 3 запити з 9 переглядів. Щоб віддати одну сторінку каталогу, API робить два запити до бази (скільки всього товарів і які на цій сторінці) і перетворює до 12 товарів у JSON.

Кеш працює так:

1. З усіх параметрів запиту (пошук, фільтри, сортування, сторінка) складається ключ. У кожної комбінації свій ключ.
2. API шукає цей ключ у Redis. Якщо знайшов — одразу віддає готову відповідь, у базу не йде.
3. Якщо не знайшов — бере дані з бази, кладе в Redis на 45 секунд і віддає.

У відповіді є заголовок `X-Cache`:

- `HIT` — відповідь з кешу;
- `MISS` — у кеші не було, взяли з бази;
- `BYPASS` — кеш вимкнено або Redis не відповідає.

За цим заголовком k6 рахує, скільки відповідей прийшло з кешу.

| Що                       | Як                                                            |
| ------------------------ | ------------------------------------------------------------- |
| Кеш                      | ElastiCache for Redis OSS 7.1, `cache.t4g.micro`, один сервер |
| Хто має доступ           | лише API і воркер, із закритої мережі, з шифруванням          |
| Скільки живе запис       | 45 с (`CACHE_TTL_SECONDS`)                                    |
| Як вимкнути              | `CACHE_ENABLED=false`, у Terraform `-var cache_enabled=false` |
| Якщо Redis не відповідає | через 0.5 с запит іде в базу                                  |

### Чому не зберігати кеш у пам'яті самого API

Копій API може бути до чотирьох, і в кожної був би свій кеш.

- Дані змінились — одна копія вже показує нове, а інша ще 45 секунд старе. Балансувальник кидає користувача то на одну, то на іншу, і дані на сторінці «стрибають».
- Нова копія стартує з порожнім кешем. А нові копії з'являються якраз тоді, коли навантаження найбільше.
- Очистити кеш можна лише в одній копії. Інші про це не дізнаються.

Один спільний Redis усе це вирішує: кеш один для всіх, нова копія одразу ним користується, а одне видалення діє для всіх.

## Як кеш показав себе під навантаженням

| Запуск          | З кешу (k6) | З кешу / з бази (за даними Redis) | Процесор Redis | Процесор бази, максимум |
| --------------- | ----------- | --------------------------------- | -------------- | ----------------------- |
| `smoke`         | 90.5 %      | —                                 | —              | —                       |
| `lab2-baseline` | 97.4 %      | 9019 / 233 (97.5 %)               | < 1 %          | 12 %                    |
| `lab2-async`    | 97.1 %      | 10 197 / 194 (98.1 %)             | < 1 %          | 9 %                     |
| `stress-80`     | 0 %\*       | 16 121 / 262 (98.4 %)             | < 1 %          | 10 %                    |

\* Це не справжні 0 %. Цей запуск ішов через CloudFront, а CloudFront замінює наш заголовок `X-Cache` своїм (`Miss from cloudfront`). k6 бачить лише його. Статистика самого Redis показує, що кеш працював як завжди. Щоб k6 бачив наш заголовок і через CloudFront, його варто перейменувати, наприклад на `X-App-Cache`.

Статистика Redis рахує ще й статуси асинхронних замовлень, тому цифри трохи відрізняються від k6.

- **З бази береться лише 2–3 % відповідей.** У тесті 12 різних варіантів каталогу, і кожен береться з бази раз на 45 секунд, коли запис у кеші закінчується. За 10 хвилин тесту це ~13 разів на варіант, тобто 12 × 13 ≈ 160. Решта — коли кілька запитів одночасно приходять на щойно застарілий запис (див. «Нашестя на базу» нижче).
- **База майже не працює.** Навіть на 88 запитах за секунду її процесор не піднімався вище 12 %.
- **У пробному запуску з кешу менше (90.5 %),** бо він тривав лише 35 секунд. За цей час кожен варіант каталогу хоча б раз брався з бази.

### Коли API перевантажений

Коли процесор API зайнятий на 100 %, він не встигає вчасно прочитати відповідь Redis. Через 0.5 с бібліотека здається і повідомляє про помилку. У логах це виглядає так:

```
WARNING app.core.cache cache read failed: Timeout reading from master.jmil-cache…:6379
WARNING app.core.cache cache read failed: Timeout connecting to server
```

Сам Redis при цьому відпочиває (процесор < 1 %) — проблема на боці API.

Для каталогу це не страшно: запит просто йде в базу з `X-Cache: BYPASS`, і користувач нічого не помічає. Для інших місць, де API читає Redis, після тестів додано загальне правило: якщо Redis не відповів, API повертає `503` («спробуйте ще раз») з підказкою `Retry-After: 1`, а не `500`.

## Застарілі дані

Після зміни даних користувач може ще до 45 секунд бачити старе — поки запис у кеші не закінчиться. Зміна в базі кеш сама не очищає.

У нашому випадку це нормально. Каталог через API не змінюється: ціни і наявність оновлює адміністратор. Замовлення каталог не змінюють.

Як зменшити цей час:

1. **Зберігати менше.** Найпростіше, але тоді частіше доведеться йти в базу. З 1 секундою кеш майже нічого не дає. З 1 годиною покупець може годину бачити стару ціну.
2. **Видаляти запис при зміні даних.** Для цього є `invalidate()` у `cache.py`. Важливий порядок: спочатку зберегти зміну в базі, потім видалити з кешу. Інакше інший запит може встигнути прочитати старі дані і знову покласти їх у кеш.
3. **Додати номер версії в ключ.** Дані змінились — номер збільшився. Старі записи просто перестають використовуватись і зникають самі.
4. **Оновлювати кеш разом з базою** (write-through).

## Нашестя на базу (cache stampede)

Коли закінчується популярний запис у кеші, багато запитів одночасно бачать, що його немає, і всі разом ідуть у базу по одне й те саме. Що з цим роблять:

- перший запит іде в базу, а решта чекають його або отримують старе значення;
- ставлять різним записам трохи різний час життя, щоб вони не закінчувались одночасно;
- оновлюють запис трохи раніше, ніж він закінчиться.

У нас лише 12 варіантів каталогу, а одне звернення в базу — це два простих запити. Тому окремого захисту я не робив.
