# Захист від повторних замовлень

Бонусне завдання 7. Код: [`api/app/core/idempotency.py`](../api/app/core/idempotency.py), використання — у [`api/app/api/v1/orders.py`](../api/app/api/v1/orders.py). Тести: [`api/tests/test_idempotency.py`](../api/tests/test_idempotency.py).

## Навіщо

Якщо двічі надіслати `POST /orders`, буде два замовлення. А повтори трапляються часто:

- сервер створив замовлення, але відповідь не дійшла (обірвався зв'язок);
- браузер або проміжний сервер сам повторив запит, бо довго не було відповіді;
- людина двічі натиснула кнопку.

Клієнт не знає, чи дійшов його запит. Якщо він повторить, а сервер не вміє розпізнати повтор, з'явиться друге замовлення і гроші спишуть двічі.

Операція, яку можна безпечно повторити скільки завгодно разів з тим самим результатом, називається **ідемпотентною**.

## Як це працює

Для кожного замовлення клієнт придумує унікальний ключ (наприклад, UUID) і передає його в заголовку `Idempotency-Key`. Якщо повторює запит — передає той самий ключ.

```
POST /api/v1/orders
Authorization: Bearer …
Idempotency-Key: 6f1d1a52-6c0e-4e4f-9a43-0d5b8e2f1c11
```

1. Сервер «займає» ключ у Redis. Це робиться однією командою (`SET … NX`), тож два запити одночасно зайняти той самий ключ не можуть. Позначка «виконується» живе 60 секунд.
2. Якщо ключ зайняв цей запит, сервер створює замовлення і запам'ятовує відповідь на 24 години.
3. Якщо ключ уже зайнятий:
   - **відповідь уже є** — сервер повертає її ще раз з позначкою `Idempotent-Replayed: true` і нічого не робить повторно;
   - **перший запит ще виконується** — `409 Conflict` («зачекайте»);
   - **з тим самим ключем прийшло інше замовлення** — `422`, бо це помилка клієнта.
4. Якщо замовлення не вдалося (наприклад, товару немає), ключ звільняється, і можна спробувати ще раз.

У кожного користувача свої ключі, тож однакові ключі в різних людей одне одному не заважають.

## Як перевірити

Основний тест — `test_same_key_creates_one_order_and_returns_same_response`. Він надсилає два однакові запити з одним ключем. У базі з'являється одне замовлення, обидві відповіді — `201` з тим самим номером, а в другої є `Idempotent-Replayed: true`.

```bash
cd api && pytest tests/test_idempotency.py -v
```

Інші тести перевіряють:

- без ключа створюються два замовлення;
- той самий ключ з іншим замовленням дає `422`;
- повтор, поки перший запит ще виконується, дає `409`;
- невдалу спробу можна повторити;
- ключі різних користувачів не перетинаються.

Перевірка на живому сервісі (для локальної копії — `URL=http://localhost:8000`):

```bash
URL=$(terraform -chdir=infra output -raw frontend_url)
TOKEN=$(curl -s -X POST "$URL/api/v1/auth/login" -d 'username=demo@jmil.dev&password=demo12345' | jq -r .access_token)
KEY=$(uuidgen)
for i in 1 2; do
  curl -s -i -X POST "$URL/api/v1/orders" -H "Authorization: Bearer $TOKEN" \
    -H "Idempotency-Key: $KEY" -H 'Content-Type: application/json' \
    -d '{"firstName":"Ann","lastName":"Pilot","phone":"+380501234567","items":[{"productId":1,"quantity":1}]}' \
    | grep -E '^HTTP|^location|^idempotent|"id"'
done
```

### Перевірка вручну

Команда вище, запущена на локальній копії (`docker compose up`, чиста база), 20 листопада 2026. До неї додано ще два запити: той самий ключ з іншою кількістю товару і два замовлення взагалі без ключа.

| #   | Запит                              | Відповідь     | `Location`         | `Idempotent-Replayed` |
| --- | ---------------------------------- | ------------- | ------------------ | --------------------- |
| 1   | з ключем                           | `201 Created` | `/api/v1/orders/1` | —                     |
| 2   | той самий ключ, те саме замовлення | `201 Created` | `/api/v1/orders/1` | `true`                |
| 3   | той самий ключ, інша кількість     | `422`         | —                  | —                     |
| 4   | без ключа                          | `201 Created` | `/api/v1/orders/2` | —                     |
| 5   | без ключа, те саме замовлення      | `201 Created` | `/api/v1/orders/3` | —                     |

Що це показує:

- **Повтор з ключем не створює нового замовлення.** Запит 2 повернув той самий номер `1`, що й запит 1, і позначку `Idempotent-Replayed: true`. Тобто сервер не виконував замовлення вдруге, а віддав збережену відповідь.
- **Ключ не можна використати для іншого замовлення.** Запит 3 відхилено з `422`.
- **Без ключа захисту немає.** Запити 4 і 5 — однакові, але створили два окремі замовлення (`2` і `3`).
- **У базі 3 замовлення, а не 5**: одне з ключем і два без нього.
- **У Redis зберігся запис** `idem:orders:1:705911c3-…`. Тут `1` — номер користувача, далі сам ключ. Запис живе 24 години: одразу після запитів до кінця лишалось 86 395 секунд.

Випадок `409` (повтор, поки перший запит ще виконується) вручну відтворити важко: замовлення створюється за мілісекунди. Тому його перевіряє тест `test_request_in_progress_is_a_conflict`.

## Як це пов'язано з чергою

Повтори треба ловити у двох місцях:

1. **Між клієнтом і API.** `POST /orders/async` теж приймає `Idempotency-Key`. Повтор повертає той самий `requestId` і не кладе в чергу друге замовлення.
2. **Між чергою і воркером.** SQS може доставити замовлення двічі. Тому в базі `request_id` унікальний, і повторна доставка не створює друге замовлення.

У результаті замовлення буде одне — скільки б разів клієнт не повторив запит і скільки б разів SQS не доставив повідомлення.
