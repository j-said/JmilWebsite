# Замовлення через чергу

Бонусне завдання 6. Код: [`api/app/api/v1/orders.py`](../api/app/api/v1/orders.py), [`api/app/worker.py`](../api/app/worker.py). Інфраструктура: [`infra/queue.tf`](../infra/queue.tf), [`infra/worker.tf`](../infra/worker.tf), масштабування — у [`infra/autoscaling.tf`](../infra/autoscaling.tf).

## Як це влаштовано

```
клієнт --POST /orders/async--> API --> черга SQS jmil-orders --> воркер --> база
       <--202 + Location------   статус у Redis <-----------------
клієнт --GET /orders/requests/{id}--> API --> Redis
```

Звичайне замовлення створюється одразу: API пише його в базу і відповідає. Тут інакше:

1. **API** перевіряє замовлення, записує в Redis статус «в черзі» (`queued`), кладе замовлення в чергу AWS SQS і одразу відповідає `202 Accepted` («прийнято»). У базу API не йде.
2. **Воркер** — окремий процес. Він бере з черги до 5 замовлень за раз і створює їх у базі. Перед цим він чекає 1 секунду — так імітується, ніби ми чекаємо відповіді платіжної системи. Потім ставить статус «готово» (`completed`) з номером замовлення або «не вдалося» (`failed`) з причиною і видаляє замовлення з черги.
3. **Кількість воркерів** залежить від довжини черги: від 20 замовлень у черзі додається 1 воркер, від 100 — 2. Якщо черга 3 хвилини порожня, один воркер прибирається. Воркерів буває від 1 до 4.

Воркер — це той самий код, що й API, просто запускається іншою командою: `python -m app.worker`.

## Що змінилось для клієнта

|                | `POST /orders`        | `POST /orders/async`                                         |
| -------------- | --------------------- | ------------------------------------------------------------ |
| Код відповіді  | `201 Created`         | `202 Accepted`                                               |
| Що в відповіді | готове замовлення     | `{"requestId": "...", "status": "queued"}`                   |
| `Location`     | `/api/v1/orders/{id}` | `/api/v1/orders/requests/{requestId}`                        |
| Що це означає  | замовлення створене   | замовлення прийняте, але ще не створене і ще може не вдатися |

Тобто після `202` клієнт ще не знає номера замовлення і має бути готовий, що воно не створиться (наприклад, товар закінчився).

### Як дізнатися результат

Клієнт час від часу перевіряє статус за адресою з `Location`:

```
GET /api/v1/orders/requests/9b0c…   ->  {"status": "queued"}
GET /api/v1/orders/requests/9b0c…   ->  {"status": "completed", "orderId": 1234}
```

Або отримує `{"status": "failed", "error": "Out of stock: …"}`. Статус зберігається 24 години, і бачить його лише той, хто зробив замовлення.

Замість постійних перевірок можна було б надсилати результат самі: через webhook, WebSocket або лист.

## Замовлення не губляться, але можуть прийти двічі

SQS обіцяє: кожне повідомлення буде доставлене **хоча б один раз**. Але інколи — двічі.

Як це працює: коли воркер бере замовлення з черги, воно не видаляється, а ховається на 60 секунд. Воркер видаляє його лише після того, як усе зробив. Якщо воркер упав або не встиг, замовлення знову з'являється в черзі, і його бере інший воркер. Так нічого не губиться.

Але є випадок: воркер створив замовлення і впав, не встигнувши видалити його з черги. Тоді замовлення буде оброблене ще раз.

Буває і навпаки — «не більше одного разу»: повідомлення видаляється одразу, і якщо обробка впала, воно втрачене. Черги зазвичай обирають перший варіант: втратити замовлення гірше, ніж отримати дубль, а дубль можна відловити.

### Як відловлюються дублі

- У кожного замовлення є унікальний `request_id`, і база не дасть записати два однакові.
- Перед створенням воркер перевіряє, чи замовлення з таким `request_id` уже є. Якщо є — просто ставить статус «готово» і видаляє повідомлення.
- Якщо два воркери взяли те саме замовлення одночасно, другий упреться в обмеження бази. Воркер це ловить і робить те саме.

Якщо замовлення не вдалося обробити 5 разів поспіль, SQS переносить його в окрему чергу для збійних повідомлень `jmil-orders-dlq`. Там його можна подивитися вручну.

Коли AWS вимикає воркер, той перестає брати нові замовлення, доробляє поточні і завершується.

## Як черга показала себе під навантаженням

Запуск `lab2-async`: 40 користувачів, кожен по колу робить `POST /orders/async` і перевіряє статус ([LOADTEST.md](LOADTEST.md)). Час — за Києвом.

| Час         | Замовлень у черзі (найбільше за хвилину) | Воркерів      |
| ----------- | ---------------------------------------- | ------------- |
| 02:17       | 26                                       | 1             |
| 02:18       | 167                                      | 1             |
| 02:19       | 226                                      | → 2           |
| 02:20       | 76                                       | → 3           |
| 02:21       | 3                                        | 3             |
| 02:22       | 1                                        | → 4           |
| 02:23–02:26 | 0–4                                      | 4             |
| 02:29–02:35 | 0                                        | 4 → 3 → 2 → 1 |

- **Один воркер не встигав.** Він обробляє до 5 замовлень за секунду (5 за раз і 1 секунда очікування). На розгоні замовлень приходило більше, і черга виросла до 226.
- **Воркери додались швидко.** Аларм на 20 замовлень у черзі спрацював о 02:19, і за 3 хвилини воркерів стало 4. Чергу розібрали за 2 хвилини. Найдовше замовлення чекало 73 секунди.
- **Четвертий воркер — трохи запізно.** Його додали о 02:22, коли черга вже була майже порожня: аларм дивиться на найбільше значення за хвилину, а там ще були старі дані. Далі 4 воркери до кінця тесту тримали чергу майже порожньою.
- **Прибирались по одному кожні 3 хвилини**, коли черга була порожня: 02:29 → 3, 02:32 → 2, 02:35 → 1.
- **Нічого не загубилось.** У чергу надіслано 2630 замовлень, оброблено 2630, у черзі для збійних — нуль.

### Чому з чергою не швидше

Порівняно зі звичайними замовленнями на тих самих 40 користувачах:

|                    | Звичайні | Через чергу |
| ------------------ | -------- | ----------- |
| Запитів за секунду | 50       | 42          |
| p95 замовлення     | 1082 мс  | 1295 мс     |
| p95 переглядів     | 706 мс   | 1073 мс     |

Черга знімає роботу з бази. Але база й так не була завантажена: її процесор не піднімався вище 12 %.

Не вистачало процесора самого API (чверть ядра на копію). А для нього відправити замовлення в чергу не легше, ніж записати в базу:

- замість одного запису в базу — запис статусу в Redis і запит до AWS SQS, який бібліотека boto3 ще й підписує;
- плюс клієнт окремо перевіряє статус — це ще один запит до Redis.

Коли процесор API був зайнятий на 100 %, 4 перевірки статусу закінчились помилкою `500`: API не дочекався відповіді Redis за 0.5 с. Тепер у такому випадку API відповідає `503` з `Retry-After: 1`, і клієнт розуміє, що треба спробувати ще раз.

**Коли черга справді допоможе:** коли повільне саме створення замовлення. Наприклад, справжня платіжна система замість 1 секунди очікування, складні операції в базі або різкі сплески замовлень, які база не витримала б. Тоді API відповідає миттєво, а воркери спокійно розбирають чергу.
